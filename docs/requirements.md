# 需求与验收账本

最新评审：2026-09-08。用户明确目标为上架 Steam，并要求先讨论整体方案，再实施改造。本次只更新需求及评审记录，不修改游戏代码、资产或线上版本。引擎选择、原创世界观和下一阶段范围均为下文建议，尚未定案。

v4 仍是功能原型。用户实玩指出持械僵硬、劈砍/前刺辨识不足、射击与枪反缺乏打击感、环境拼贴感强。R01、R02、R04、R05、R08 的相关体验验收重新打开；功能接入、敌人/武器数量和自动化测试通过不能替代动作、美术与可玩性验收。

### R09/R10：动作和反馈验收

- 背包图标仅用于 UI 和相应展示，不直接当作战斗用武器素材。手持素材有明确握点、枪口/刀尖和前后遮挡约定；角色身体与武器共享同一动作定义。
- 刀、剑、长柄刺击、斧、枪、炮、双持分别建立动作规格；同类武器可以复用经过验收的动作，不能仅换图标/数值就算新增玩法。下一样板先覆盖哪些类别待讨论，现有多武器需求保留。
- 命中判定以战斗模拟为准，身体姿态、武器轨迹、有效帧、音效与特效使用统一时序；不能刀未到先扣血，或动作已经收回仍持续伤害。
- 快速枪械可以采用即时射线，慢速炮弹可以采用可见弹体；二者均需让枪口、可见轨迹、遮挡和实际命中点一致。不能把是否使用物理弹体等同于打击感好坏。
- 关闭刀光和粒子后，仍能从身体姿态分辨劈砍/前刺、轻重动作；恢复特效后增强这些动作，不遮挡敌人预警、接触点和后续操作。
- 正常速度验收手感；逐帧检查只用于握点、轮廓、命中帧和遮挡。测试需同时覆盖击空、命中、被挡、受击中断、死亡、暂停恢复及动作取消。
- 声音需有武器身份和接触材质差异；枪反成功、处决和普通命中不能只共享一种爆闪/噪声。震屏和闪光有强度控制与减少动态效果选项。

### R11：防止环境拼贴感的长期约束

适用于现有两个章节以及以后所有新区域。2D 贴图本身不是缺陷；缺陷是物体像独立贴纸、占位矩形或悬空道具。

1. **空间依附**：窗户嵌在完整墙体/建筑剖面中，有窗洞、窗框、窗台及合理厚度；门和通道有墙体、门洞、地面衔接和进出空间。梯子必须连接可到达的上下平台，并有固定点；楼梯、平台应有梁柱、墙托或符合世界观的支撑。
2. **层级与材质**：远景、中景建筑、游戏平面和前景具有明确关系；遮挡、光向、局部投影、环境色和接触阴影一致。灯光作用于附近建筑表面；窗内光从洞口透出。色块拼装、杂乱方块堆叠或通用方框不能作为完成美术提交。
3. **统一像素语言**：先通过样板确定基准分辨率、角色尺寸、像素密度和材质细节等级。不能用放大粗像素、全局模糊、发光或噪点滤镜掩盖材质和切片问题。字体保持清晰。
4. **交互可信**：可攀爬、可通行、单向捷径、锁门、隐蔽路线的视觉规则一致；画面可见范围应与碰撞及触发区域匹配。转场由玩家进入真实通道触发，并有方向和目的地反馈。
5. **静态与动态双验收**：关闭标签、光效和粒子后，仍能理解墙、窗、门、梯子与地面的关系；走动、转身、攀爬和进出通道时检查脚底、手部、遮挡、视差和镜头运动。仅能靠文字说明用途的占位物不算完成。
6. **源资产可维护**：保留可编辑模型/动画或像素源文件、无损图集母版、切片及握点元数据。发布压缩图不能成为唯一制作源；生成候选图需完成结构、风格和切片检查后再入库。

## 2026-09-08 核查证据

依据用户截图 `07f6997a-60f1-4561-a04c-14d94530ed46.png` 及 GitHub v4 源码 `36daad0b79e01e95ef1a8b66f378ebf1f6329026` 静态核查；本轮没有重新进行完整实玩或浏览器回归。

- `pixel-scene.js::drawWeapon` 从 `equipment-v4` 背包图集中裁手持武器；`actor` 使用固定的 `handX/handY` 和角度插值，未采用逐帧握点。`pose` 的三段攻击各仅切换两张身体姿态，爬梯复用了行走行。
- `campaign.js::fireWeapon` 清空近战攻击状态并即时筛选前方目标；`pixel-scene.js::event` 主要显示短时直线与火星，没有与身体姿态联动的专属持枪/后坐阶段。
- `engine.js::attackUpdate` 主要按前方距离和高度差判断命中，武器外观轨迹独立由渲染器计算；二者缺少统一的可编辑招式定义。
- `pixel-scene.js::huntLandmarks` 使用矩形/路径绘制灯、梯子、传送框和独立窗户，缺少配套中景建筑结构。截图中的悬空窗和无墙门框是当前实现结果，并非完成场景美术。
- `main.js` 的声音主要为合成振荡器与噪声层，尚未建立武器、接触材质与环境尾响的声音制作规范。

## 后续方向建议，待讨论

- 产品主轴建议为“原创哥特探索动作冒险”：固定相连区域和持续剧情为骨架，战斗强调机动、枪反和武器差异，装备提供少量可理解的联动。如何采用精力、双持及长线成长需一起确定，不能把多个参考游戏的规则直接累加。
- 商业表达需单独讨论原创世界、人物、故事和视觉设计；当前沿用的亚南、加斯科因等内容不能因标注致敬而视为已获得商业授权。可学习气氛、风险回报和探索结构；具体改写方案尚未执行。
- 制作路线建议先验证一个可编辑的角色/武器动画样板：Blender 绑定与关键姿势动画 → 低分辨率输出 → 像素修整 → 导入引擎；纯手绘逐帧为可比较的备选。不会直接批量生成完整动作图集作为最终动画。
- 技术路线倾向评估 Godot 2D + Blender；同时保留现有 JavaScript 方案作为成本基准。迁移应依据样板的动画编辑、关卡制作、桌面输入/输出成本再决定。现有固定步长、行为回归、存档规则、内容数据和已验证设计具有复用价值，渲染/UI 及运行逻辑不承诺无成本移植。
- 最小架构只围绕可调动作、碰撞、装备/遭遇数据、关卡连接和版本化存档建立明确边界。沿用已有事件流；避免为了重构先造通用 ECS、脚本语言或自研关卡引擎。

## 已知限制

- 场景和身体动画仍有共用帧；处决没有完整专属骨骼动作。
- 关卡为固定布局；隐藏裂墙是一次性调查/奖励交互，尚无完整可破坏地形系统。
- 秘法雷葬与冰霜暂共用一组冰晶图集，机制与配色不同；后续需要独立雷电资产。
- 未复现原作全部敌人变种、支线失败条件或后期地图。
- 自动保存限当前浏览器，跨设备需导出导入。
- 全部地图总敌人点为 36；两位 Boss 包含在内，不另加。
