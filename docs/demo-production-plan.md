# Deadblood：AI 协作 Demo 制作计划

2026-09-08。讨论稿，承接 [R09–R12](requirements.md)。本轮交付制作计划；尚未安装引擎、迁移源码、制作动画或部署新游戏。下列范围、工时及参数是建议，不代表用户已确认或已完成。

## 1. 要验证什么

建议采用 Blender 离线制作角色动画、导出二维帧，Godot 2D 运行游戏。第一个交付是“一个角色的一次劈砍，在游戏内正确命中一个敌人”，随后用同一工程扩成 15–20 分钟探索 Demo。

验证依次为：制作流程能否稳定重做 → 操作和交战是否成立 → 场景是否统一 → 探索/装备/故事是否形成体验。现有 v4 的功能数量不能作为新样板质量依据。

最终 Demo 建议：一个安全营地、4–6 个相连房间；刀、长柄刺击、手枪三种动作代表；3 类小怪、1 精英、1 个两阶段 Boss；一条支线、一条捷径、两种配装取舍；一个短开场和可见的事件后果。斧、炮、双持及两个完整区域保留为后续需求。

暂缓内容扩量：全面换装外观、全稀有度独立模型、大技能树、随机地图、复杂制作配方和新章节。房间、角色和动作样板通过后再安排这些成本。

## 2. 工具与工程起步

| 工具/位置 | 负责什么 | 首个验收物 |
| --- | --- | --- |
| Godot 稳定版 + GDScript | 控制器、战斗模拟、场景、UI、音频、存档和桌面输出 | `game/` 内可打开、可运行的战斗房间 |
| Blender 稳定版 | 模型、骨骼、关键姿势、相机和批量渲染 | 可编辑角色 `.blend` 和一次攻击动作 |
| 像素编辑器 | 检查并修整轮廓、透明边、颜色、闪烁 | 无损 PNG 动画序列及游戏内观察结果 |
| 可访问本地工程与命令行的代码 AI | GDScript、Blender Python、导出/检查工具、行为测试 | 能复现的修改与验证记录 |
| GitHub `eldenmoon/deadblood` | 源码、原始资产、版本和任务依据 | 每次修改可回溯，下一任务基于同一工程 |

将 Godot 工程新增到现有仓库的 `game/`，Blender 源文件放在 `art-src/`，批量导出工具放在 `tools/`。保留 `dist/` 作为既有浏览器原型，不在其上运行脚手架，也不先搬迁全部内容。大型源资产再按实际体积采用 Git LFS；导出目录和临时视频区别于制作源。

先锁定机器上验证可用的具体工具版本、启动路径和一次运行命令。Godot 用 GDScript 有利于保留后续 Web 试玩选择；当前官方文档说明 Godot 4 的 C# 项目不能导出 Web。第一阶段优先本机桌面试玩，若计划 Steam 首发 Windows，早期同时验证 Windows 构建和一次实际运行；Web 是可选体验渠道，不代替桌面验证。

用户负责准备可用本机环境、确认角色与画风、实际试玩；AI 可以在获得本地工程及可执行工具访问后协助操作。仅有网页聊天并不等同于可以操作用户电脑上的 Blender 或 Godot。

## 3. Blender 到二维动画的完整流程

### 3.1 先做一个可编辑的人形

先选一具许可允许使用的基础绑定人形，或做简洁的原创绑定样板。把主要精力用于角色轮廓、手臂腿部比例、衣摆和武器可读性。第一轮保留一种角色外观，集中修改少量大形体。AI 生成模型需先检查关节、分件和权重能否支持动作；概念图或自动模型不是绑定动画成品。

### 3.2 固定游戏视角与像素规格

建议试验值：游戏逻辑视口 640×360，站立角色约 64–80 逻辑像素高，正交相机采用固定侧面略带体积的视角。实际尺寸以一屏战斗距离和辨识度决定，样板阶段可以调整，通过后锁定。

相机比例、光照、角色基线和颜色处理全动作一致。为长兵器和举手动作预留画布；禁止逐帧按包围盒缩放、自动居中，否则角色会忽大忽小、脚底漂移。逻辑碰撞和物理坐标保留精度，只在最终显示阶段处理像素对齐。

### 3.3 先调关键姿势

从预备、发力、穿过目标、收招几个姿势开始。劈砍检查蹬地、转髋、送肩和刃口轨迹；前刺检查身体推进、双手支撑和枪尖稳定；射击检查举枪、枪口方向与肩臂后坐。随后调整停留与快速过渡，避免所有关键帧匀速插值。

先验收一次劈砍，再扩展待机、跑、跳落、闪避、受击、死亡、三段连击、刺击、射击、处决、攀爬等。动作可以采用不均匀帧时长；动画采样率与游戏 60 Hz 模拟时钟分开，不用强制补满 60 张图片实现流畅。

### 3.4 身体与武器先一起烘焙

Demo 优先按代表武器/动作组合将身体和武器一起渲染，保证握持和遮挡自然。握点在 Blender 绑定中，枪口、刀尖、地面基线等锚点同步导出为元数据。UI 图标另行制作。

同族武器可绑定到同一套动画离线重渲染。每件武器和每种服装仍会增加输出量，不能把骨骼复用当成免费换装。等样板稳定后再评估分层身体/武器及绘制顺序，避免第一步就建立任意装备组合系统。双手长柄切换副手枪反时也必须有合理的收起/举枪姿态。

### 3.5 输出序列与帧信息

交付透明背景、统一画布的无损 RGBA PNG 序列、帧时长、基线/锚点元数据，以及可复现的导出脚本。Blender 支持图像序列输出和命令行后台渲染，可由 Python 辅助自动化。

在实际目标像素尺寸检查透明软边、细节闪烁与颜色一致性；必要时比较采样方式和像素修整结果。Blender 的默认渲染并不自动等于原作的自制像素渲染器。运动模糊和强降噪不用于掩盖不清晰的关键姿势。

初期使用稳定烘焙明暗、游戏内环境色与接触阴影。法线贴图和角色动态受光在基础效果通过后评估，不作为第一招的前置工作。发布压缩图不能代替源文件和无损母版。

### 3.6 接入游戏与反馈

使用一份招式时序定义前摇、有效窗口、后摇、输入缓存、取消窗口及反馈事件。模拟时钟推进状态，显示动画与之对应；修改时序后必须能重新预览。用少量命中形状近似刃口轨迹，快速动作按需要扫掠采样，不追求逐像素碰撞。

同一动作标记对齐挥动声、枪口光、后坐、命中、受击与停顿。高速枪械可用射线；炮弹可用可见弹体，均需正确处理遮挡和接触点。先保留原有“动作结束后控制必释放”的回归约束。

## 4. 依赖顺序、分工与退出条件

| 阶段 | 要完成的工作 | AI 主要负责 | 用户主要负责 | 通过条件 |
| --- | --- | --- | --- | --- |
| D0 一招闭环 | 一具绑定人形、一次劈砍、一个敌人/受击靶、一个 Godot 房间 | 工程接入、渲染模板/脚本、元数据、命中与重置 | 提供/确认可用人形，查看姿势与实际大小，按键试玩 | 改姿势→重导出→游戏重播可复现；武器不脱手；命中与画面一致 |
| D1 战斗房间 | 刀连段、长柄刺击、手枪/枪反、闪避、受击、处决及一类有预警的敌人 | 控制器、招式数据、反馈集成、复现/边界回归 | 反复试打，调整节奏；确认发力与声音 | 无特效也可读；打空、打中和被挡有区别；不会靠同一无限连击压制一切 |
| D2 场景样板 | 一间完整街巷：墙、门洞、窗、梯、平台支撑、局部光、前后景 | 导入、碰撞、交互、镜头与资产检查 | 确认统一美术标准与行走中的空间关系 | 静态和运动均无悬空贴纸感；与 R11 一致；字体清晰 |
| D3 体验切片 | 15–20 分钟回环探索，内容按第 1 节逐项接入 | 数据/场景复用、敌群、掉落/装备、简单剧情旗标与存档 | 选路线、调遭遇和资源，确认章节情绪 | 能无辅助完成；捷径改变返程；两种配装有取舍；支线/Boss 后有后果 |
| D4 外部试玩 | 找 5–8 位未参与制作的人试玩；形成下一轮问题清单 | 记录设施、问题归类、定点修复与验证 | 观察试玩，决定优先级和保留/删除机制 | 无阻断与坏档；玩家理解目标和主要失败原因；能给出明确的战斗/探索反馈 |

D0 是成本和能力验证，D1 是动作验证，D2 是画面质量门槛；D3 应沿用前述工程和角色，而不是另起一个 Demo。每次只进入已经有前置成果的一项任务。玩法粗布局可用于测试，但占位几何必须明确标识，不能作为 D2 的完成美术。

测试分三种：行为回归检查状态/伤害/存档；正常速度和逐帧视频检查动作/画面；外部试玩检查理解、策略和乐趣。5–8 人是找问题的小样本，不能证明 Steam 商业销量。

## 5. 初始排期与首批工作

排期假设：用户负责主程和产品决策，每周约 20 小时；代码 AI 可运行项目；已有可用绑定基础，或可获得少量动画支持。建议预留 8–12 周作为首轮工作窗口，不是完成或发布承诺。若模型、权重与关键动画都从零学习，D0 后必须按实际投入重估。

| 时间窗口 | 主要交付 |
| --- | --- |
| 第 1–2 周 | D0，测出一招从源文件到游戏的制作/修改成本 |
| 第 3–4 周 | D1，以实际操控校准移动、连段、枪反和反馈 |
| 第 5–6 周 | D2，确定可复用的场景构件与美术规格 |
| 第 7–9 周 | D3，组合路线、敌群、装备选择、短支线和 Boss |
| 第 10–12 周 | D4，补齐已发现问题并决定下一阶段范围 |

8 周仅在样板和素材顺利、部分工作能够重叠时争取；任何前置门槛不通过就重排后续窗口。先记录实际小时，避免把计划表上的日期当成质量达标。

最开始按以下五个工作单元推进：

1. 安装并运行 Godot/Blender；检出仓库；记录版本；新增 `game/`，验证空房间能在目标桌面启动。
2. 选定一具可用绑定人形和一把刀；锁定临时相机及像素规格，输出一张站立帧放入游戏观察。
3. 制作一次劈砍的关键姿势和时序；输出统一画布序列及基线信息。
4. 接入一次攻击、一个受击目标、一次重置；对齐判定、身体与武器。
5. 加入必要声音与接触反馈；录正常速度及慢放片段；用户实际按键验收。通过后进入 D1。

这些是工作顺序，不是五天完工承诺。绑定或动作制作遇到问题应在对应单元解决，不用新增武器、菜单或剧情代替该交付。

## 6. 如何让 AI 持续参与

| 工作 | 适合交给 AI 的部分 | 仍需人工负责 |
| --- | --- | --- |
| 角色/场景概念 | 方向候选、轮廓比较、色板和参考整理 | 选定统一方向、原创辨识、最终质量判断 |
| 模型与动画 | Blender 场景模板、批处理、初步绑定/关键帧辅助、问题定位 | 形体、权重、发力、节奏和像素清理；无法自动保证商业质量 |
| 游戏代码 | GDScript、编辑器资源、控制器、战斗与存档、回归检查 | 功能优先级、关键架构选择、手感试玩 |
| 声音 | 事件时序、分层与混音接入、整理有使用权的候选素材 | 音色选择、响度对比、材质与空间感验收 |
| 测试/管理 | 复现步骤、输入回放、崩溃/性能记录、PR 和变更说明 | 外部玩家观察、是否好玩的判断、是否进入下一阶段 |

建议只用一个主工程和一个任务队列。每次任务包含：阶段、现有文件、玩家问题、限制、可运行交付、验收证据。代码修改应直接落入工作树并运行验证；交付不止是聊天里的代码。需要 Blender 实际渲染时使用已安装工具的脚本或命令行，不要求先安装特定 MCP；工具未接通就明确报告能力边界。

每次回报保留可试玩构建、短片段或必要截图、改动文件、验证结果与剩余问题。记录手部/脚部/命中帧等具体问题，避免只要求“高级一点”。前期若有预算，优先考虑一具可编辑角色及关键动作的专业制作/校正；具体采购、外包对象与费用另行确认。

### 第一条实施任务提示词（用户决定开工后使用）

```text
基于 eldenmoon/deadblood 开始 D0“一招闭环”。先读取 AGENTS.md、docs/requirements.md 和 docs/demo-production-plan.md。

目标：在同一仓库的 Godot 2D 工程中，让一具可编辑的绑定人形持刀完成一次劈砍，并在正确时刻命中一个受击目标。

先检查本机 Godot、Blender 和源资产是否可用，再按 D0 顺序实现。沿用仓库工作成果，保留现有 dist 原型。首次缺少可用绑定角色时，完成可验证的工程/导出准备，并清楚说明资产缺口；不得把粗糙色块人标为最终角色。

交付：可打开的 Godot 工程、可编辑 .blend、透明 PNG 序列、基线/握点或刀尖元数据、可复现导出方式、可试玩房间，以及验证记录。

验收：身体和武器共同发力，握持/遮挡正确，脚底和尺寸稳定，命中与有效帧一致，攻击结束或被打断后控制恢复；能够修改一个姿势并重新导出验证。打空与命中分别录制正常速度片段，逐帧查看不能代替实玩。

范围只到 D0；不提前扩地图、武器库、背包或完整剧情。未实际运行、渲染、试玩的项目必须标记为未验证，不能用测试数量替代美术和手感验收。
```
